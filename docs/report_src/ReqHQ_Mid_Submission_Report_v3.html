1. Project overview

Product requirement documents (PRDs) are usually strong on what a system should do and weak on how well it should do it: performance budgets, security expectations and reliability targets are often missing, vague, or scattered across long documents. Writing a complete specification from such a PRD is slow, and a single-pass LLM draft inherits the same gaps. Our project builds an agentic pipeline that turns a rough PRD into a complete, trace-linked specification: every line in the final spec names where it came from - a verbatim PRD sentence, a specialist critic, or a human answer.

The system has four cooperating components:

  • Orchestrator. Reads the PRD and drafts functional requirements, each traced to the exact PRD sentence it came from.
  • Specialist critics. Three reviewers - Security, Architecture and Performance - inspect the draft and the PRD for missing or vague non-functional requirements. Each finding quotes the PRD sentence that triggered it and explains why it matters.
  • Gap-and-conflict check. Applies the proposal's escalation rule: the human is asked only for missing business context or critic disagreement; fixes a critic can make itself are repaired directly and marked not user-confirmed.
  • Trace-linked composer. Produces the final specification grouped into functional requirements and NFR categories, downloadable as JSON or Markdown, with a trace report counting how every line is grounded.

Later stages train small specialist models (SLMs) to replace the LLM critics, and evaluate the whole system on frozen dataset splits against these hypotheses.

2. Research hypotheses (verbatim from the submitted proposal)

H1. The full pipeline (without human input) has higher NFR recall than a single LLM given the same PRD, with precision dropping by no more than 0.03.
H2. SLM critics come within 0.05 NFR F1 of LLM critics in the same roles, at much lower token cost and latency.
H3. Targeted questioning reaches at least 95% of the completeness of asking the human to review everything, using at least 50% fewer questions.

No hypothesis results are claimed at this checkpoint; scoring runs only after the gold set is fully human-verified (Section 3).

3. Work completed

3.1 Stage 1 - Working PRD-to-spec pipeline

The full loop from raw PRD text to a downloadable, trace-linked specification works end to end. The code is organized as a small, testable core (src/specpipe/: schemas, LLM client, orchestrator, critics, gap check, pipeline) behind a Streamlit UI. A deterministic mock model runs the whole application offline without an API key, and is used for development and tests. The trained classifier is not yet integrated, so the hosted demo shows the flow with demo-mode output, not model quality; demo-mode output is never used for evaluation.

3.2 User interface

A guided three-step wizard: (1) Describe - paste a PRD or load a bundled sample and analyse it; (2) Review & answer - inspect draft FRs with their PRD traces and critic findings, answering only the questions the system cannot settle; (3) Specification - the final trace-linked spec, downloadable as JSON or Markdown.

3.3 Stage 2 - Frozen datasets and the gold protocol

Two datasets are frozen under data/frozen/ with manifests, provenance and license documentation: PROMISE NFR (classification subtask) and PURE (61 requirement documents for the end-to-end evaluation). The dev/test split is fixed and the test split stays untouched until the Stage 4 evaluation, so no iterative tuning can leak into final numbers.

Because PURE ships without per-requirement NFR gold labels, we built a two-step ground-truth protocol:

  • LLM-suggested labels. A free-tier model proposed requirement labels for the 61 dev documents, recorded with status “LLM-SUGGESTED - unverified, not gold”. The evaluation loader rejects these fail-closed: unverified suggestions can never be scored as gold.
  • Anchored human verification. Two annotators verify the suggestions with fixed written guidelines and a paging review tool that records exactly how many characters were presented and read. Documents are split into two unique parts plus a shared subsample reviewed independently by both; anchored accept/reject agreement (Cohen’s kappa) is computed on the shared docs at merge time.
  • Fail-closed merge. A document is promoted to FROZEN gold only when every suggestion has a verified resolution and the annotator confirmed reading the full scope. Any skip, tie, contested edit or incomplete read makes the whole document review-incomplete and ineligible for scoring - there is no partial-gold scoring.

3.6 Stage 4 - Evaluation harness and pre-freeze generation

The evaluation harness is built and documented (docs/evaluation.md, decisions D1-D4): a frozen-split runner with baselines B1-B4, gold loading that refuses unverified documents, a matching rubric, and per-run JSONL logs. On 6 November we ran bounded pre-freeze generation over the dev split: 43 of 61 documents now hold complete B1+B2+B3 output triplets with persisted requirements, bounded to the same 120k-character prefix scope the gold protocol uses. The run stopped cleanly on the free-tier daily request quota with 18 documents not yet generated. These outputs are unscored, only the complete triplets form the comparable subset, and no evaluation metric is claimed in this report.

4. Known gaps, carried honestly

  • Gold coverage is scope-bounded. The LLM pre-labeler and human review see at most the first 120,000 characters per document (18 of 61 dev documents are longer); dev scoring uses the same bound and no full-document recall is claimed.
  • FR/NFR typing is a keyword heuristic in the orchestrator, unvalidated; the Stage 2 guidelines and matching rubric own the real boundary.
  • Unseeded training makes classifier quality vary run to run (Section 3.5); seeded training and a reproducibility check are open work.
  • “0 untraced lines” means trace coverage only - every line names a source; it says nothing about correctness, which is exactly what the frozen-split evaluation will measure.
  • Evaluation is not scored yet. Generation outputs exist for 43/61 dev documents; extending gold coverage beyond the 3 frozen documents, and the quota-blocked rubric scoring, are the immediate next steps.
